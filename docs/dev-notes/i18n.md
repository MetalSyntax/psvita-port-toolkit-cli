# `i18n.py` — Developer Notes

This file collects the *why* behind `i18n.py` that doesn't belong in the code itself as Doxygen
documentation (which only covers the *what*: brief/param/return). Read this if you're adding a
new translated string, wondering why there's no `.po`/gettext setup, or touching the fallback
logic in `t()`.

## Why a hand-rolled dict instead of gettext/.po files

This toolkit's text volume is small enough that a full gettext pipeline (`.po`/`.mo` compilation,
`xgettext` extraction, locale directories) would be pure overhead. A single in-memory dict,
populated by each module registering its own strings at import time, covers the need with zero
external dependencies and zero build step.

## The registration pattern, in full

Each module that wants translated strings declares its own dict and registers it once, at import
time, right after its imports:

```python
from . import i18n
from .i18n import t

STRINGS = {
    "init_port.game_name_prompt": {
        "es": "Nombre del juego (display, ej. 'Inotia 4'):",
        "en": "Game name (display, e.g. 'Inotia 4'):",
        "pt": "Nome do jogo (exibição, ex. 'Inotia 4'):",
    },
}
i18n.register(STRINGS)

...
input(t("init_port.game_name_prompt"))
```

Keys are namespaced with the owning module's name as a prefix (`"init_port.game_name_prompt"`,
`"config.language_prompt"`, etc.) specifically so that two modules can never accidentally clobber
each other's key. `register()` does a plain dict `update()` — if the same key *is* reused across
two modules despite the convention, whichever module registers last silently wins, with no error
raised. The namespacing convention is the only thing preventing that collision, so don't drop it
when adding a new module.

Values that need runtime data use `str.format()` placeholders:

```python
"init_port.summary_game": {"es": "  Juego:    {name}", ...}
...
print(t("init_port.summary_game", name=game_name))
```

## Fallback behavior in `t()`, and why it's forgiving rather than strict

`t()` deliberately never raises for a bad or missing key:

- An unregistered key returns the key string itself. The reasoning: a visible key like
  `"init_port.game_name_prompt"` printed to the user is an ugly but recoverable bug (and an
  obvious signal to go fix the missing translation), whereas a `KeyError` would crash whatever
  menu or prompt loop happens to be running at that moment.
- If the key exists but has no entry for the currently active language, it falls back to
  `DEFAULT_LANGUAGE` (Spanish), and if even that's missing, to the first translation available in
  the dict (`next(iter(entry.values()), key)`). This means a string can be added in only one
  language as a stopgap without breaking anything for users running the toolkit in a different
  language.
- If `str.format(**kwargs)` fails (wrong/missing placeholder), `t()` returns the raw unformatted
  text rather than raising — again prioritizing "something readable on screen" over crashing.

## Language bootstrap ordering (why `t()` "just works" everywhere else)

The active language is decided exactly once per run. `config.py`'s `ensure_language()` asks the
user on first run (or loads the saved choice from `~/.psvita-toolkit/config.json` on subsequent
runs) and calls `set_language()` before any other menu or prompt is shown. By the time the rest
of the toolkit executes, `t()` is already resolving to the correct language — no module needs to
think about language selection itself, it just calls `t()`.
